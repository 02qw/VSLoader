# v96 更新器进度与详情实时滚动编码规格说明

## 1. 背景

当前 `VSLoader.Updater` 已经具备阶段性进度展示能力，主窗口会在更新过程中不断刷新：

- 进度条
- 状态文本
- 详情日志列表

用户希望这部分表现更像“实时滚动”的更新控制台，而不是只在少数几个节点跳一下。

经分析，当前 updater 本身已经通过 `Progress<T>` + UI 刷新实现了基本的实时更新能力，不需要再额外引入一层“后台异步再套后台异步”的复杂结构。真正需要的是：

- 保持现有更新流程稳定
- 让进度和详情在 UI 上持续、可见、顺滑地滚动
- 避免因为线程处理不当导致崩溃

## 2. 目标

本次优化目标是：

- updater 的进度条在更新过程中连续、及时地反映当前阶段。
- 详情日志列表在新增日志时自动滚动到最新行。
- 仍然保持更新逻辑由后台任务执行，UI 只负责展示。
- 不引入额外的后台日志线程、消息队列或复杂动画框架。
- 不破坏现有更新主流程、错误处理、回滚逻辑和 releaseNotes 展示逻辑。

## 3. 方案选择

### 方案 A：沿用现有 `Progress<T>` + UI 刷新

这是推荐方案。

做法：

- 更新服务继续在关键阶段调用 `IProgress<UpdaterProgress>`
- UI 线程收到回调后，立即更新进度条、状态文本和详情列表
- 详情列表使用 `ScrollIntoView` 自动滚到最后一条

优点：

- 改动最小
- 稳定性最好
- 不会增加跨线程集合访问风险
- 性能开销低

缺点：

- 不是“每帧动画式”的滚动
- 只是阶段性实时刷新

### 方案 B：UI 节流刷新

如果后续发现日志过密，可以在 UI 层增加一个轻量节流机制，将短时间内多次更新合并为一次刷新。

本次不强制实现，作为后续增强项。

### 方案 C：后台队列 + 定时器刷新

把进度/日志先放入队列，再由 UI 定时取出刷新。

本次不采用。

原因：

- 复杂度高
- 目前更新阶段数有限
- 容易引入额外同步问题

## 4. 实现原则

### 4.1 进度刷新只保留一条主链路

更新进度只走现有链路：

- `UpdaterUpdateService.RunAsync(...)`
- `Progress<UpdaterProgress>`
- `MainWindow.SetProgress(...)`

不新增第二套异步刷新链路。

### 4.2 详情日志只允许 UI 线程写入

`DetailLines` 仍然保持为主窗口内的 `ObservableCollection<string>`。

所有写入必须在 UI 线程执行，避免跨线程集合访问导致崩溃。

### 4.3 详情滚动跟随最新项

每次新增一条详情日志后：

- 自动滚动到最后一条
- 保持最新阶段可见

### 4.4 不做花哨动画

进度条不做复杂补间动画，不做额外视觉特效。

原因：

- updater 的首要目标是稳定
- 简单明确的进度反馈比动画更重要

## 5. 关键逻辑

### 5.1 进度更新

在 `MainWindow` 中继续使用现有的：

```csharp
private void SetProgress(int value, string text)
```

要求：

- `ProgressValue` 更新进度条
- `StatusText` 更新状态文字
- `DetailLines.Add(...)` 追加一条日志
- `DetailList.ScrollIntoView(...)` 滚到最后

### 5.2 更新服务输出

`UpdaterUpdateService` 保持按阶段报告进度：

- 正在读取更新信息
- 已读取更新内容
- 当前版本与服务器版本对比
- 正在复制更新包
- 正在校验 SHA256
- 正在解压更新包
- 正在备份旧版本
- 正在替换程序文件
- 更新完成

每个阶段都应是明确的、低频的，不需要高频刷屏。

### 5.3 错误态处理

如果更新失败：

- 进度可以停在最后有效阶段
- 详情列表保留最后几条关键日志
- 错误信息通过 `StatusText` 明确显示
- 更新内容区域按已有错误态规则隐藏

## 6. 稳定性要求

### 6.1 不允许跨线程直接改集合

如果将来要增加新的日志来源，必须保证：

- `DetailLines.Add` 仍在 UI 线程执行
- 不直接从后台线程写 `ObservableCollection`

### 6.2 不要把滚动逻辑放到后台线程

`ScrollIntoView` 必须跟随 UI 线程执行。

### 6.3 不要引入高频轮询

不需要使用毫秒级 Timer 不停刷新界面。

当前 updater 的更新步骤不是高频事件，轮询反而徒增复杂度。

## 7. 性能要求

- 现有阶段式刷新即可满足需求
- 不额外引入后台日志缓存
- 不额外引入消息泵或动画帧逻辑
- 保证界面不卡、逻辑简单

## 8. 测试要求

建议至少覆盖：

1. 进度更新会追加详情行
   - 调用 `SetProgress` 后，详情列表新增一条记录

2. 最新记录会自动可见
   - 详情列表新增后应滚到最后一条

3. 更新服务仍按阶段输出
   - manifest 读取
   - 版本比较
   - 解压
   - 替换
   - 完成

4. 错误场景不影响主线程稳定性
   - 不引入跨线程集合修改
   - 不引入额外崩溃点

## 9. 验收标准

满足以下条件即算完成：

- updater 更新过程中进度条持续可见变化
- 详情列表持续追加并自动滚动到底部
- 不新增后台线程复杂度
- 不增加跨线程崩溃风险
- `dotnet test .\\VSLoader.sln -c Debug` 通过
- `dotnet build .\\VSLoader.sln -c Debug` 通过
